# 부하 측정 결과 (2차, 2026-11-24)

이 폴더는 [`tools/loadgen`](../../tools/loadgen)으로 최종 서버를 잰 원자료와 요약이다. 아래 결과 표는 `summarize.py`가 원자료에서 만든 [tables.md](tables.md)를 그대로 옮겼다. 회차마다 한 줄은 [summary.csv](summary.csv), 조건별 평균 · 최소 · 최대는 [summary_agg.csv](summary_agg.csv)에 있다.

## 1. 무엇을 쟀나

| 이름 | 조건 | 반복 |
|---|---|---|
| S1 규모 | TCP, 손실 0, netem 없음, 봇 100 · 500 · 1000 · 2000 · 4000 | 60초 × 3회 |
| S2 전송 비교 | 봇 200, netem 지연 20ms, 손실 0 · 1 · 5%, TCP 대 UDP | 60초 × 3회 |
| 자체 검증 | 봇 2개(경기 하나), TCP · UDP × netem 지연 0 · 20ms | 20초 × 3회 |
| 다시 하기 검증 | 봇 2개, 1점 경기(`win_score` 1), TCP · UDP | 20초 × 1회 |

47회 모두 정상으로 끝났다(서버 · 도구가 도중에 죽거나 접속이 실패한 회차 없음).

## 2. 환경

| 항목 | 값 |
|---|---|
| 기계 | Windows 노트북, Intel Core Ultra 7 258V, 컨테이너에서 보이는 코어 8개 |
| 가상화 | Docker Desktop WSL2 VM(커널 6.18.58.1-microsoft-standard-WSL2), 메모리 15.4GiB |
| 컨테이너 | `gcc:14`(Debian 13, gcc 14.4.0), `--cap-add NET_ADMIN --ulimit nofile=65536:65536` |
| 서버 | `make dist`(-O2, sanitizer 없음, 정적 링크), `--port 7777 --stats-interval 1 --quiet`, UDP 켬 |
| 서버 소스 | 커밋 `8f08ee5` + 커밋 전 작업 트리(바뀐 파일 63개). 소스 · 바이너리 해시는 [env.txt](env.txt) |
| 도구 | loadgen -O2, 한 프로세스 · 한 스레드 epoll |

- **서버와 도구는 같은 컨테이너, 같은 CPU에서 돈다.** 4000봇에서 도구가 코어 하나의 약 50%, 서버가 약 61%를 쓴다. 서로 CPU를 다툰다.
- 같은 시간에 다른 컨테이너(다른 담당자의 Unity 확인용 서버 등)와 Windows 프로그램이 함께 돌았을 수 있다. 회차마다 시작 · 끝의 Docker VM 부하(`/proc/loadavg`)를 `meta.json`과 summary.csv에 남겼다. 1분 평균 최대는 1.15였다.
- netem은 루프백(`lo`)에 건다. `lo`는 보내는 쪽과 받는 쪽이 같은 장치라 **지연 · 손실이 서버로 갈 때와 돌아올 때 두 번 걸린다.** 지연 20ms는 왕복 약 40ms가 되고, 손실 p%는 한 방향마다 p%다(질문과 답이 모두 와야 하는 일은 대략 2p%로 실패한다).

## 3. 봇이 하는 일

- 봇 둘이 짝이다. 짝수 봇이 비공개 방을 만들고(규칙은 protocol.md 6.1절 기본값에 `win_score`만 21), 홀수 봇이 그 코드로 `JOIN_BY_CODE` 한다. 경기가 끝나면 `REMATCH`를 보낸다.
- 60초 측정 안에 21점 경기는 끝나지 않는다. 그래서 S1 · S2는 경기 중 구간만 잰다. 다시 하기 경로는 1점 경기 검증으로 따로 확인했다.
- 입력은 `MATCH_START`를 받은 시각 + n × 1000/30ms에 보낸다(6.1절). 도구가 밀렸으면 밀린 입력을 몰아 보내 개수를 맞춘다. `input_seq`는 경기마다 1부터 센다.
- 패들은 공 y에 노림 오차를 더한 곳으로 간다. 오차는 공이 자기 쪽으로 오기 시작할 때마다 ±80 안에서 다시 뽑아, 가끔 놓쳐 득점이 난다.
- UDP 모드는 7장대로 묶는다(0.2초마다 다시 보내고 2초 안에 답이 없으면 TCP만 씀). 묶인 뒤 `GAME_IN`은 묶음 형식(방금 입력 + 직전 최대 3개)으로 UDP에 보낸다. 이번 S2에서는 200봇 모두 묶였고 TCP로 돌아간 봇은 0이다.
- 접속은 초당 약 400개로 나눠 연다(봇 수 / 400초, 최소 2초). 마지막 접속 뒤 3초가 지나면 60초 측정 구간이 시작된다. 지연 · 간격 · 개수는 측정 구간 것만 센다.

## 4. 지표

| 이름 | 뜻 |
|---|---|
| 입력 반영 지연 | 입력을 보낸 시각부터, 그 `input_seq`가 `STATE.last_input_seq`로 처음 나타난 `STATE`를 받은 시각까지 |
| 반영 안 된 입력 | `last_input_seq`가 건너뛴 번호 수. TCP에서는 서버 입력 큐(4개)가 넘쳐 버려진 입력이다. UDP에서는 그 번호를 담은 `STATE`가 사라진 경우도 들어간다(그래서 tick 건너뜀 비율과 거의 같다) |
| STATE 간격 | 받아들인 `STATE` 사이의 시간 |
| tick 건너뜀 비율 | 건너뛴 tick 수 / (받은 tick 수 + 건너뛴 tick 수) |
| 순서 뒤바뀜 | 이미 받은 것보다 tick이 작거나 같은 `STATE` 수(7장대로 버림) |
| RTT | 봇마다 1초에 한 번 `PING` → `PONG`(TCP) |
| 한 진행 넘게 늦게 보낸 입력 | 도구가 예정 시각보다 33.3ms 넘게 늦게 보낸 입력 수. 접속을 여는 동안을 포함한 실행 전체. 0이 아니면 도구가 한 번 이상 멈췄다 |
| 서버 진행 처리 | 서버 stats의 `tick_us_p99`(한 진행 시각에 모든 방의 진행을 처리한 시간). 1초 줄마다의 p99 중 측정 구간 줄들의 중앙값과 최대 |
| 버린 진행 | 서버가 밀려 버린 진행 수(5.2절 8번), stats `ticks_dropped` 합 |
| 서버 RSS · CPU | 측정 구간의 stats 줄. CPU %는 (user + sys) / 구간 시간, 코어 하나 = 100% |
| 도구 CPU | loadgen의 `getrusage`, 측정 구간 |

분위수는 0.1ms 칸 고정 히스토그램(0-5000ms)에서 칸의 위쪽 끝으로 구한다. 실제 값보다 최대 0.1ms 크게 나온다.

## 6. 읽는 법

### S1 규모

- 모든 봇 수 · 모든 회차에서 접속은 전부 성공했고(4000봇도 4000/4000), 접속 뒤 끊김과 버린 진행은 0이다.
- 서버 진행 처리 p99(초별 중앙값, 3회 평균)는 100봇 17µs에서 4000봇 132µs다. 진행 간격 33.3ms에 비하면 작다.
- 서버 CPU는 100봇 2.5%, 1000봇 17.2%, 2000봇 30.4%, 4000봇 61.3%(코어 하나 기준)로 봇 수에 거의 비례한다. RSS는 1.2MB에서 14.6MB다.
- 입력 반영 지연 p50은 15회 중 12회가 33.4-33.5ms(진행 간격 한 번)다. 나머지 3회는 진행 간격 단위로 커진 채 굳었다.

| 회차 | 입력 지연 p50 · p99 ms | 반영 안 된 입력 | 한 진행 넘게 늦게 보낸 입력 | 도구 송신 밀림 최대 ms (실행 전체) |
|---|---|---|---|---|
| 500봇 2회차 | 66.7 · 100.2 | 0 | 0 | 2.3 |
| 4000봇 1회차 | 100.3 · 133.7 | 2427 | 4000 | 57.6 |
| 4000봇 3회차 | 34.6 · 133.7 | 2352 | 4000 | 64.3 |

- 4000봇에서 지연이 커진 두 회차는 둘 다 도구가 실행 중 한 번 크게 멈춘 회차다(봇마다 늦은 입력이 하나씩, 4000개). 멈추지 않은 2회차는 33.5 · 34.0ms다. 이 두 회차의 4000봇 지연은 서버가 아니라 도구의 멈춤이 섞인 값으로 본다.
- 500봇 2회차는 도구가 멈추지 않았고(최대 2.3ms) 버려진 입력도 없는데 지연이 진행 한 번만큼 커졌다. 도구 밖(서버 · 커널 · VM)에서 입력이 한 진행 넘게 늦게 읽힌 것으로 추정한다. 이 자료로는 어디서 늦었는지 가르지 못한다.
- 왜 한 번 늦으면 굳나(protocol.md 6.1절 규칙에서 따라 나옴): 서버는 진행마다 큐에서 입력을 **하나만** 꺼내고, 비면 직전 입력을 다시 쓴다. 입력이 한 진행보다 늦게 도착하면 그 진행은 큐가 비어 있고, 늦은 입력은 다음 입력과 함께 큐에 남는다. 클라이언트는 같은 간격으로 계속 보내므로 큐는 그 뒤로 줄지 않는다. 그래서 한 번의 멈춤이 경기가 끝날 때까지 진행 간격 하나(33.3ms)씩 지연을 더하고, 큐 상한 4개에서 멈춘다(넘치면 오래된 입력을 버림).

### S2 전송 비교 (지연 20ms)

- 손실 0에서는 TCP와 UDP가 같다: 입력 지연 p50 66.8ms, p99 67.5 · 67.6ms. 왕복 40ms가 진행 간격 33.3ms보다 길어 입력이 진행 한 번 뒤에 쓰인다.
- 손실이 있으면 UDP가 낮다. 3회의 범위가 서로 겹치지 않는다.

| 손실 | TCP p50 · p99 ms | UDP p50 · p99 ms | TCP STATE 간격 p99 ms | UDP STATE 간격 p99 ms |
|---|---|---|---|---|
| 1% | 133.5 · 206.7 | 100.1 · 134.0 | 84.9 | 50.5 |
| 5% | 166.8 · 280.6 | 133.4 · 167.3 | 106.9 | 66.8 |

- TCP는 `STATE`를 잃지 않지만(건너뜀 0), 재전송을 기다리는 동안 입력과 상태가 한꺼번에 밀려 STATE 간격 p99가 84.9 · 106.9ms로 늘어난다. 손실 5%에서는 큐가 넘쳐 버려진 입력이 회차마다 2868-2966개다.
- UDP는 `STATE`를 잃는다. tick 건너뜀이 1.00% · 5.04%로 한 방향 손실률과 같다. 잃은 상태는 다음 진행의 상태가 대신하므로 STATE 간격 p99는 진행 두 번(66.8ms) 안에 있다.
- UDP도 손실이 생기면 손실 0보다 입력 지연이 진행 한 번(1%) · 두 번(5%) 늘어난다. 잃은 데이터그램의 입력은 다음 묶음에 실려 한 진행 늦게 도착하므로, 위 S1에서 설명한 것과 같이 큐가 늘어난 채 남는 것으로 추정한다.
- 순서 뒤바뀜은 모든 회차에서 0이다. netem을 고정 지연으로 걸어 순서가 바뀌지 않는 조건이다.
- RTT p50은 손실과 상관없이 40.1-40.2ms다(PING은 TCP라 잃어도 재전송된다. p50에는 드러나지 않는다).

### 자체 검증

- 봇 2개, netem 없음: 입력 반영 지연 p50 33.5ms, p99 34.1ms 이하로 진행 간격 33.3ms 안팎이다.
- netem 지연 20ms를 걸면 RTT p50이 TCP 0.20 → 40.30ms, UDP 0.23 → 40.27ms로 약 40ms 늘어난다. 지연이 왕복에 두 번 걸린 값과 맞다.
- 같은 조건의 입력 반영 지연은 67.2-67.5ms다. 왕복 40ms가 진행 간격보다 길어 진행 한 번 뒤에 쓰인 값이다.
- 다시 하기: 1점 경기 20초 동안 TCP · UDP 모두 경기 4번이 시작됐고, 다시 한 경기에서도 입력 지연은 33.4 · 33.5ms 그대로다.

## 7. 측정의 한계

- 서버와 도구가 같은 기계 · 같은 CPU를 나눠 쓴다. 다른 컨테이너와 Windows 프로그램도 함께 돌았을 수 있고, `loadavg`는 Docker VM 안만 본다.
- 도구가 한 프로세스라 4000봇에서 코어 하나의 절반을 쓰고, 3회 중 2회는 실행 중 한 번 57-64ms 멈췄다. 이 멈춤이 지연 결과를 바꿨다. 4000봇보다 많이 재려면 도구를 여러 프로세스로 나눠야 한다.
- 큐가 한 번 늘면 경기 끝까지 남으므로, 회차 결과는 "60초 동안 한 번이라도 한 진행 넘게 늦었나"에 크게 갈린다. 3회로는 그 확률을 말할 수 없다. 흩어짐은 최소-최대로만 적었다.
- 루프백이라 실제 네트워크의 대역폭 제한 · 흔들림 · 순서 뒤바뀜이 없다. netem은 고정 지연과 독립 손실만 흉내 낸다. 손실률은 한 방향 값이다.
- 21점 경기가 60초 안에 끝나지 않아 경기 시작 · 다시 하기가 몰리는 순간의 부하는 S1 · S2에 들어 있지 않다.
- 서버 진행 처리 시간은 서버가 스스로 잰 값이다. 서버 프로세스가 CPU를 받지 못한 시간은 들어가지 않는다.
- 분위수는 0.1ms 칸이라 0.1ms 아래 차이는 가리지 못한다.
- 서버는 커밋 전 작업 트리로 빌드했다. 같은 서버인지는 [env.txt](env.txt)의 소스 해시로 확인한다.

## 8. 다시 돌리기

호스트의 Git Bash에서(스크립트가 `gcc:14` 컨테이너를 띄워 그 안에서 다시 실행한다):

```bash
REPS=3 DUR=60 ./tools/loadgen/bench.sh selfcheck s1 s2
```

`REPS`(반복, 기본 3), `DUR`(측정 초, 기본 60), `SC_DUR`(자체 검증 측정 초, 기본 20), `OUT`(결과 폴더, 기본 `/src/docs/report-data`)을 바꿀 수 있다. 같은 이름의 회차 폴더는 지우고 다시 쓴다. 표만 다시 만들려면:

```bash
python3 tools/loadgen/summarize.py docs/report-data
```
