# ADR 0002: 서버를 공통 영역과 게임 모듈로 나누고, 게임은 정해진 약속으로만 붙인다

- 상태: 결정됨 (2026-11-21)
- 결정한 사람: 프로젝트 담당자

## 배경

- 처음 설계는 메인 루프가 Pong을 직접 부르고, 입력 · 상태 메시지가 Pong 형식으로 프로토콜에 고정되어 있었다. 방 인원(2명)과 진행 간격(30Hz)도 서버 전체에 고정이었다.
- 이대로면 다른 게임을 붙일 때마다 서버 핵심 코드를 고쳐야 하고, 서버가 계산하지 않고 전달만 하는 방식(릴레이)은 넣을 수 없다.
- 접속, 메시지 자르기, 로비, 방, 진행 시계는 어떤 게임이든 같다.
- 현업 게임 서버(Nakama, Colyseus, Photon 등)도 로비 · 방 · 접속을 공통으로 두고 게임 로직을 따로 붙인다.

## 결정

1. **서버 코드**를 공통 영역(코어)과 게임 모듈로 나눈다. 둘 사이의 약속은 `server/src/game_api.h` 하나다.
   - 게임 모듈은 `game_def`(게임 번호, 이름, 최소 · 최대 인원, 진행 간격, 입력 길이 상한, 함수 6개)를 하나 내놓는다.
   - 코어는 `game_def`의 함수만 부르고, 게임은 코어가 준 `game_host`(보내기 · 모두에게 보내기 · 경기 끝내기)로만 플레이어에게 데이터를 보낸다.
   - 게임은 보낼 때 "반드시 도착(신뢰)" 또는 "최신 것만 중요(비신뢰)"만 고른다. TCP인지 UDP인지는 코어가 정한다(ADR 0001의 2차와 맞물림).
2. **프로토콜**을 공통 메시지와 게임 메시지로 나눈다.
   - type 번호의 높은 두 비트로 방향(클라이언트 → 서버, 서버 → 클라이언트)과 층(공통, 게임)을 구분한다.
   - 게임 메시지는 `GAME_IN`(0x40)과 `GAME_OUT`(0xC0) 두 개뿐이다. 코어는 길이만 검사하고 내용은 게임이 정한다.
   - 접속 직후 서버가 `WELCOME`으로 등록된 게임 목록을 알려 준다.
3. **이번에 만드는 게임**은 두 개다.
   - Pong(`game_id` 1): 서버가 30Hz로 계산하는 권위적 방식.
   - Relay(`game_id` 2): 서버는 계산 없이 같은 방에 전달만 한다.
4. **Unity 클라이언트**도 같은 경계로 공통 부분(접속 · 로비)과 게임 부분(Pong)을 나눈다.

## 결과

- 좋은 점
  - 새 게임은 코어를 고치지 않고 게임 모듈 하나, 등록 목록 한 줄, protocol.md 6장의 절 하나로 붙는다.
  - 같은 서버에서 권위적 방식과 릴레이 방식을 함께 돌리고 부하를 비교할 수 있다.
  - 코어 테스트와 게임 테스트를 따로 할 수 있다. Pong 진행 함수는 네트워크 없이 단위 테스트한다.
- 대가
  - 함수 포인터 표 한 겹이 생긴다. 호출 비용은 진행 한 번에 방마다 몇 번 수준이라 무시할 만하다(측정 전 추정).
  - 게임 메시지 안에 종류 바이트를 하나 더 둔다(Pong의 `STATE` · `GOAL`). 메시지마다 1바이트.
  - 인원과 진행 간격이 방마다 달라져서, 진행 시계와 방 상태 처리가 조금 일반적이 된다.
- 확인한 것: 이 약속만 보고 Relay 게임을 만들 수 있는지, 가짜 코어 위에서 throwaway 프로그램으로 돌려 봤다(2026-11-21). 3명 방에서 slot 1이 보낸 데이터를 slot 0 · 2만 한 번씩 받았고, `-Wall -Wextra -Wpedantic -Werror`와 ASan/UBSan에서 경고 · 보고가 없었다.

## 다시 볼 조건

- 한 방에서 여러 게임을 이어서 하는 기능(경기가 끝난 뒤 같은 방에서 다시 시작)이 필요해지면, 지금의 "경기가 끝나면 방을 닫는다" 규칙(protocol.md 5.2절)을 바꾼다.
- 게임 모듈이 코어에 더 많은 기능(타이머, 저장)을 요구하기 시작하면 `game_host`에 함수를 더하기 전에 정말 공통인지 먼저 따진다.
