# ADR 0001: 전송 계층은 TCP로 먼저 완성하고, 게임 데이터만 UDP로 옮겨 비교한다

- 상태: 결정됨 (2026-11-20)
- 결정한 사람: 프로젝트 담당자

## 배경

- 서버는 30Hz로 게임을 진행하고, 클라이언트는 33ms마다 입력을, 서버는 33ms마다 게임 상태를 보낸다.
- TCP는 사라진 패킷을 다시 보낼 때까지 뒤 데이터를 붙잡는다(헤드오브라인 블로킹). 리눅스의 재전송 대기는 최소 200ms다. 학습 자료 07의 시뮬레이션에서 5% 손실일 때 지연 p95가 UDP형 69ms, TCP형 216ms였다.
- UDP는 이 지연이 없지만, 꼭 도착해야 하는 메시지의 재전송, 연결 · 끊김 관리, 클라이언트 식별을 직접 만들어야 한다.
- 마감은 2026-12-06(결정 시점에서 16일). 서버, Unity 클라이언트, 부하 테스트를 모두 끝내야 한다.
- 실시간 대전 게임은 대체로 UDP를 쓰고, 턴제 · 웹 게임과 Colyseus · Nakama 같은 게임 서버는 TCP(WebSocket)를 기본으로 쓴다.

## 검토한 안

| 안 | 내용 | 추가 작업 | 판단 |
|---|---|---|---|
| A | TCP만 | 없음 | 가장 안전하지만 손실 환경의 한계를 말로만 설명하게 된다 |
| B | TCP로 먼저 완성, 여유가 있으면 입력 · 게임 상태만 UDP로 옮겨 비교 | 2–3일 (추정) | **채택** |
| C | 처음부터 TCP + UDP | 초반 일정이 2–3일 밀림 | 최종 모습은 B와 같고, 위험만 앞당긴다 |

## 결정

**B**를 따른다.

1. **1차**: 모든 메시지를 TCP 한 연결로 보낸다. `TCP_NODELAY`로 작은 패킷을 묶어 늦게 보내는 동작(Nagle)을 끈다.
2. **2차** (11/28까지 Unity 대전이 되면 12/01–12/02에 진행):
   - TCP에 남기는 것: 로비 · 방 만들기 · 입장 · 퇴장 · 득점 · 경기 종료 · 오류. 꼭 도착해야 한다.
   - UDP로 옮기는 것: 입력과 게임 상태. 33ms마다 새로 보내므로 하나가 사라져도 다음 것으로 메워진다.
   - UDP 쪽에는 재전송을 만들지 않는다. 대신 입력 패킷에 직전 입력 몇 개를 함께 실어 하나가 사라져도 서버가 채울 수 있게 하고, 게임 상태는 가장 최신 것만 쓴다.
   - TCP와 UDP를 서버 실행 옵션으로 바꿀 수 있게 하고, 같은 조건(손실률, 지연)에서 둘을 측정해 report.md에 비교한다.
3. 처음부터 게임 데이터를 보내는 코드를 한 모듈(`channel`)에 모아, 2차에서 그 모듈만 바꾸게 한다.

## 결과

- 좋은 점: 1차만으로도 완성된 결과물이 나온다. 2차가 되면 "TCP 대신 UDP를 쓰면 얼마나 좋아지는가"를 직접 잰 수치로 보일 수 있다.
- 대가:
  - 1차 결과물은 패킷 손실이 있는 네트워크에서 가끔 멈칫거린다. 보고서에 한계로 적는다.
  - 프로토콜 명세는 TCP 프레임과 UDP 데이터그램 두 경우를 모두 다뤄야 한다.
  - 2차에서는 UDP 패킷이 어느 플레이어의 것인지 확인하는 방법(TCP로 받은 토큰을 UDP 패킷에 싣기 등)이 필요하다. protocol.md에서 정한다.
  - 데모 서버(Oracle Micro)의 방화벽에서 UDP 포트도 열어야 한다.
- 입력 번호: 입력에는 클라이언트가 붙이는 순서 번호를 쓴다. TCP에서는 순서대로 도착하므로 이것으로 충분하고, UDP에서도 같은 번호로 중복과 빠진 입력을 가려낼 수 있다.
